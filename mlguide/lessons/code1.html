Every ML job interview, from a start-up to Google, has at least one round where you write a small program while someone watches. The problems are not hard maths; they test whether you can turn a plain-English request into correct, tidy code and say how fast it runs. This lesson teaches you a calm, repeatable method for doing that, gives you a first feel for “how fast” (Big-O), and then walks you through ten warm-up problems.

You'll use Python I (lists, strings, functions) Python II (loops, dictionaries, comprehensions)

By the end of this lesson you can

  • solve a small coding problem with the five-step method: read, work examples by hand, brute force first, improve, test the edge cases;
  • write your own tests with assert before you press Check;
  • say the running time of a short function in Big-O (O(1), O(log n), O(n), O(n log n), O(n²)) and explain it in plain words;
  • solve ten classic warm-up problems (running sum, maximum, vowels, reversing, palindromes, BitByte, second largest, de-duplication, merging, missing number) and trace each one by hand.

What a coding interview actually checks

In a coding round you get a short problem, such as “given a list of numbers, return the second largest”. You have 20 to 45 minutes. You talk while you think, you write a function, and you test it. The interviewer is watching four things:

  1. Understanding. Did you ask about the unclear parts (What if the list is empty? Can numbers repeat?) before you started typing?
  2. Correctness. Does the code give the right answer for every allowed input, including the awkward ones?
  3. Efficiency. Can you say how the running time grows when the input gets bigger, and can you do better than the slowest obvious method?
  4. Communication. Can they follow your thinking? Clear names, a short explanation, a hand trace of one example.

Notice that “knowing a trick” is not on the list. Tricks help, and over these four practice lessons you will collect the dozen patterns that solve most interview problems. But the biggest difference between candidates is method: the people who do well follow the same calm steps every time. So we start there.

For ML roles in particular: the coding round is usually easier than for pure software roles (think “easy” and “medium” problems on practice sites), but ML interviewers add their own favourites: compute a mean and standard deviation without a library, one-hot encode labels, build a confusion matrix, compute the overlap of two bounding boxes. You will write all of those in Coding practice 4. Today is about the habits that make them easy.

The five-step method

Here is the method. Learn its five names; you will use them in every problem of this lesson and in every interview.

StepWhat you doWhat you say out loud
1. ReadRead the problem twice. Name the input (what type? can it be empty?) and the output (what type? what if there is no answer?).“So I get a list of integers, possibly empty, and I return one integer, or None if…”
2. Examples by handTake a tiny example and solve it with pencil and paper, slowly. Watch what you do: that is your algorithm.“For [3, 1, 4] I would look at 3, then 1, then 4, remembering the biggest so far…”
3. Brute force firstWrite the simplest correct method, even if it is slow. A slow correct answer beats a fast wrong one.“The obvious way is to try every pair; that is O(n²).”
4. ImproveAsk: what work am I repeating? Can I remember something instead of recomputing it? Can one pass do it?“I keep re-adding the same numbers. If I keep a running total, one pass is enough: O(n).”
5. Test edge casesRun the examples, then the awkward inputs: empty, one element, all the same, negatives, very large.“Empty list gives 0. One element gives itself. All negatives still works because I start from the first element, not from 0.”

An edge case is an input at the boundary of what is allowed: the empty list, a list with one item, the largest allowed number, a string with only spaces. Most bugs in interview code live in edge cases, because the brain naturally tests the “normal” example and forgets the rest.

The method on a real problem

Let us use the method once, slowly, on a problem that is not one of the ten. Read each step, and try to say the next one before you reveal it.

Worked example · count the warmer days
Problem: you are given a list of daily temperatures, for example [30, 32, 31, 35, 35, 36]. Return how many days were strictly warmer than the day before.
  1. Read. Input: a list of numbers (temperatures in °C), maybe empty. Output: one whole number, a count. The first day has no “day before”, so it can never count. “Strictly warmer” means equal does not count.Saying the input and output types out loud catches half of all misunderstandings.
  2. Example by hand. Compare each day with the one before it:
    day itemps[i−1]temps[i]warmer?count so far
    13032yes1
    23231no1
    33135yes2
    43535no (equal)2
    53536yes3
    The answer is 3. What did my hand do? It walked from day 1 to the last day, compared with the previous day, and kept a count.The table you make by hand is the algorithm. Each column becomes a variable.
  3. Brute force. Here the obvious method is already good: one loop over i = 1, 2, …, n−1, add 1 to a counter when temps[i] > temps[i-1].
  4. Improve. Each day is looked at a fixed number of times (twice), so the work grows in step with the number of days. That is the best possible: we must at least look at every day once. Nothing to improve.Knowing when to stop improving is part of the skill.
  5. Edge cases. Empty list: the loop runs zero times, answer 0. One day: the loop range(1, 1) is empty, answer 0. All equal, e.g. [20, 20, 20]: answer 0. Falling temperatures, negative numbers such as [-5, -3]: answer 1, because −3 is warmer than −5.
One loop, one counter: answer 3 for the example, and 0 for the empty list.

New in this lesson

assert condition, message checks that condition is true. If it is, nothing happens. If it is false, Python stops with an AssertionError and shows your message. It is the quickest way to write a test: assert add(2, 2) == 4, "2 + 2 should be 4". The Check button of every exercise is just a list of asserts.

a, b = b, a swaps two variables in one line: Python first builds the pair on the right, (b, a), then unpacks it into the names on the left.

None is Python's value for “no answer”. Test for it with x is None.

def count_warmer(temps):
    count = 0
    for i in range(1, len(temps)):      # i = 1, 2, ..., n-1: every day that has a day before it
        if temps[i] > temps[i - 1]:
            count = count + 1
    return count

How fast is it? Counting steps, then Big-O

Two correct programs can differ enormously in speed. To compare them without a stopwatch (which depends on your laptop), we count basic steps: one addition, one comparison, one look-up of xs[i]. Then we ask a single question: when the input gets bigger, how fast does the number of steps grow?

Counting steps by hand

Let \(n\) (read n) be the size of the input, for example the length of the list. Look at these three functions and count how many times the innermost line runs:

For a list of length 1000, how many times does the inner line of all_pairs run?

  1. 1,000
  2. 2,000
  3. 1,000,000
  4. It depends on the values in the list
The outer loop runs 1000 times, and each of those runs the inner loop 1000 times: \(1000\times1000=1{,}000{,}000\). Two loops one after the other would be 2,000; two loops one inside the other multiply. The values do not matter here because nothing in the loops depends on them.
def single_pass(xs):
    steps = 0
    for x in xs:
        steps += 1          # "steps += 1" is short for "steps = steps + 1"
    return steps

def all_pairs(xs):
    steps = 0
    for x in xs:
        for y in xs:
            steps += 1
    return steps

for n in [10, 100, 1000]:
    xs = list(range(n))
    print(f"n = {n:5d}   single pass: {single_pass(xs):8d} steps   all pairs: {all_pairs(xs):9d} steps")
Read the output: each time \(n\) grows ten times, the single pass grows ten times too, but all pairs grows a hundred times. That difference, not the exact counts, is what Big-O describes. (f"{n:5d}" prints the number right-aligned in 5 characters so the columns line up.)

Big-O in plain words

Big-O notation is a short way to say how the number of steps grows with \(n\), ignoring details that do not matter when \(n\) is large. We write \(O(n)\), read “big-O of n” or “order n”, for “the steps grow in proportion to \(n\)”, and \(O(n^2)\), read “order n squared”, for “the steps grow like \(n\) times \(n\)”.

Two rules turn an exact count into a Big-O:

  1. Keep only the biggest term. If the count is \(n^2+n\), then for \(n=1000\) that is \(1{,}000{,}000+1{,}000\); the \(n\) part is a rounding error. So \(n^2+n\) is \(O(n^2)\).
  2. Drop constant multipliers. \(3n\) and \(n\) grow the same way: doubling \(n\) doubles both. So \(3n\) is \(O(n)\). Constants depend on the computer and the language; growth does not.
What \(f(n)=O(g(n))\) means
\[f(n)=O\big(g(n)\big)\quad\text{if there is a constant } c \text{ with } f(n)\le c\,g(n)\ \text{for all large enough } n\]

Read: “f of n is big-O of g of n” if, once n is big enough, f is never more than some fixed multiple of g. In words: g is a ceiling on the growth of f, up to a constant factor.

SymbolSay it as / meaningTiny example
\(n\)“n”: the size of the input (length of the list or string)\(n=5\) for [3,1,4,1,5]
\(f(n)\)“f of n”: the exact number of steps your code takes for size \(n\)\(f(n)=3n+2\)

Worked example · turning a step count into Big-O
A function does 2 set-up steps, then a loop with 5 steps per element, then a double loop with 3 steps per pair: \(f(n)=3n^2+5n+2\).
  1. Put in numbers to see which term wins. At \(n=10\): \(3\cdot100+5\cdot10+2=300+50+2=352\); the \(n^2\) term is already \(300/352\approx 85\%\) of the total.
  2. At \(n=1000\): \(3{,}000{,}000+5{,}000+2=3{,}005{,}002\); the \(n^2\) term is \(99.8\%\). The smaller terms vanish.This is rule 1: keep only the biggest term.
  3. Keep \(3n^2\), drop the 3 (rule 2): \(f(n)=O(n^2)\). Check the definition: with \(c=4\), is \(3n^2+5n+2\le 4n^2\)? That needs \(5n+2\le n^2\), which is true for every \(n\ge 6\) (at \(n=6\): \(32\le 36\)).
\(3n^2+5n+2=O(n^2)\): doubling \(n\) roughly quadruples the work.

The five growth rates you will meet

Almost every interview answer is one of these five. Learn them as a ladder, from fastest to slowest:

Big-OName, said aloudTypical codeSteps at n = 1,000Steps at n = 1,000,000
\(O(1)\)constant: “order one”xs[i], len(xs), xs.append(v), a dict look-up11
\(O(\log n)\)logarithmic: “order log n”halving the search range each step (binary search, Coding practice 3)1020
\(O(n)\)linear: “order n”one loop over the input; sum(xs); v in xs for a list1,0001,000,000
\(O(n\log n)\)“n log n”sorted(xs); good sorting algorithms10,00020,000,000
\(O(n^2)\)quadratic: “order n squared”a loop inside a loop over the same input; trying every pair1,000,0001,000,000,000,000

Python does roughly ten million simple steps per second. So at \(n\) = one million, an \(O(n)\) method takes about a tenth of a second, an \(O(n\log n)\) method two seconds, and an \(O(n^2)\) method about 28 hours. That is why interviewers care.

Where does \(\log n\) come from? Whenever each step halves what is left. Start with \(n=1000\) and halve: 1000, 500, 250, 125, 63, 32, 16, 8, 4, 2, 1. That is 10 halvings, and indeed \(\log_2 1000\approx 9.97\). The logarithm answers “how many halvings?”. Since it grows so slowly (a million needs only 20), \(O(\log n)\) is almost as good as \(O(1)\).

You have met this before. The DFT computed straight from its definition multiplies every one of the \(N\) inputs by every one of the \(N\) twiddle factors: \(N^2\) multiplications. The FFT splits the problem in half again and again, giving \(\log_2 N\) stages of butterflies with about \(N\) operations each: \(N\log_2 N\). For \(N=1024\) that is about a million operations versus about ten thousand, a hundredfold speed-up. That gap between \(O(N^2)\) and \(O(N\log N)\) is exactly the gap between a slow and a good interview answer.

Start in “zoom in”: for small n all five curves look close. Drag n from 4 to 8 to 16: the O(n) dot doubles each time, the O(n²) dot quadruples and soon leaves the window. Switch to “y up to n²”: now O(1), O(log n) and even O(n) look flat on the floor. Finally try “log scale”, where each grid line is ten times the one below; the curves become well separated and you can read all of them at once.

Space complexity

The same notation also measures memory: how much extra storage your code needs on top of the input. A loop with two or three number variables uses \(O(1)\) extra space. Building a new list as long as the input uses \(O(n)\) extra space. When an interviewer asks “can you do it in place?”, they mean “with \(O(1)\) extra space, changing the input list itself”.

Measuring it for real

Counting steps is the theory; a stopwatch confirms it. time.perf_counter() reads a precise clock in seconds. If doubling \(n\) doubles the time, the method behaves like \(O(n)\); if it quadruples, like \(O(n^2)\).

import time

def time_it(func, xs):
    start = time.perf_counter()
    func(xs)
    return time.perf_counter() - start

for n in [500, 1000, 2000]:
    xs = list(range(n))
    t1 = time_it(single_pass, xs)
    t2 = time_it(all_pairs, xs)
    print(f"n = {n:4d}   single pass {t1*1000:7.3f} ms   all pairs {t2*1000:8.1f} ms")
Read the output: your exact milliseconds will differ from the reference output (they depend on the computer), but the ratios should not: each doubling of n roughly doubles the single-pass time and roughly quadruples the all-pairs time. Small timings are noisy, so the single-pass column may wobble.

Hidden loops. Some single lines of Python are loops in disguise. v in xs on a list checks the items one by one: \(O(n)\). xs.index(v), xs.count(v), sum(xs), max(xs), xs[a:b] (copies \(b-a\) items) and xs.insert(0, v) are all \(O(n)\) too. So for x in xs: if x in other_list: … is a loop inside a loop: \(O(n^2)\), even though you only typed one for.

Do [1, 2, 3, 4] by hand. To get the third answer, 6, do you need to add 1 + 2 + 3 again, or can you use the previous answer, 3?

Keep one variable total, starting at 0. For each number: add it to total, then append total to result.

sum(nums[:i+1]) for every i gives the right numbers but is \(O(n^2)\): each slice re-adds everything before it. The tests will time out on that.

def running_sum(nums):
    result = []
    total = 0
    for x in nums:
        total += x            # total is now nums[0] + ... + x
        result.append(total)
    return result

The idea. The sum up to position i equals the sum up to position i−1, plus nums[i]. So we never need to start adding from the beginning again; we carry the previous total forward. This “remember what you already computed” move is the most common improvement in all of algorithm design.

Complexity. One pass, constant work per number: O(n) time. The output list has n items: O(n) space for the result (and O(1) extra besides it). The brute force with slices does \(1+2+\dots+n=\frac{n(n+1)}{2}\) additions, which is \(O(n^2)\).

Edge cases. Empty input: the loop never runs and [] comes back. Negatives need nothing special.

A running sum is a discrete-time integrator, \(y[n]=y[n-1]+x[n]\): an IIR filter with one state variable. You will meet it again as the “prefix sum” trick in Coding practice 4.

By hand, you look at the numbers one by one and keep the biggest you have seen so far in your head. Make that a variable.

What should “biggest so far” start as? If you start it at 0, what happens for [-5, -2, -9]? Start it at the first number instead, after dealing with the empty list.

def largest(nums):
    if len(nums) == 0:          # edge case first: no numbers, no answer
        return None
    best = nums[0]              # the biggest we have seen so far
    for x in nums[1:]:
        if x > best:
            best = x
    return best

The idea. Keep a single “champion”, best. Each new number challenges it; the winner stays. After the last challenger, the champion is the largest. Starting from nums[0] rather than 0 is the key detail: 0 would wrongly beat every number of an all-negative list.

Strictly, nums[1:] makes a copy, which is O(n) space; if you want to avoid it, loop with for i in range(1, len(nums)) and use nums[i]. No method can be faster than O(n): any number you skip might be the largest.

def count_vowels(text):
    count = 0
    for ch in text:
        if ch.lower() in "aeiou":
            count += 1
    return count

The idea. Visit each character once and ask one yes/no question. ch.lower() turns "A" into "a" and leaves other characters alone, so one test covers both cases. "a" in "aeiou" asks whether the text "a" appears inside "aeiou".

    assert list(_xs) == _exp, f"{_case} should become {_exp}, but the list is now {list(_xs)}"
    assert _ret is None, f"reverse_in_place should change the list and return None, but it returned {_ret!r}"

By hand: swap the first and last items, then the second and second-to-last, and so on. When do you stop?

Use two positions: left = 0 and right = len(xs) - 1. While left < right: swap xs[left], xs[right] = xs[right], xs[left], then move left up by one and right down by one.

def reverse_in_place(xs):
    left, right = 0, len(xs) - 1
    while left < right:                       # stop when the two positions meet or cross
        xs[left], xs[right] = xs[right], xs[left]
        left += 1
        right -= 1

The idea. This is your first two-pointer algorithm: two positions start at the two ends and walk towards each other. Each swap puts two items in their final places, so after about \(n/2\) swaps everything is reversed. The loop condition left < right stops exactly when the pointers meet (odd length: the middle item stays put) or cross (even length).

Complexity. \(\lfloor n/2\rfloor\) swaps (read: “n over two, rounded down”): O(n) time, and O(1) extra space because we only keep two numbers. Building xs[::-1] would also be O(n) time but O(n) extra space.

Why “returns nothing”? Python's own list.sort() and list.reverse() follow the same convention: a function that changes its input returns None, so nobody mistakes it for a function that makes a copy.

def is_palindrome(text):
    clean = [ch.lower() for ch in text if ch.isalnum()]
    left, right = 0, len(clean) - 1
    while left < right:
        if clean[left] != clean[right]:
            return False          # one mismatch is enough to say no
        left += 1
        right -= 1
    return True                   # no mismatch found (also covers empty and one-letter strings)

The idea. Clean first, then compare mirror positions from the outside in. The first mismatch proves it is not a palindrome, so we can stop early. If the pointers meet without a mismatch, every mirror pair matched.

For each x there are three cases. If first is None or x > first: the old first becomes second, and x becomes first. Else if x < first and (second is None or x > second): x becomes second. Otherwise (x == first, or x is too small): nothing changes.

def second_largest(nums):
    first = None     # largest value seen so far
    second = None    # largest value seen so far that is strictly smaller than first
    for x in nums:
        if first is None or x > first:
            second = first           # the old champion is now runner-up
            first = x
        elif x < first and (second is None or x > second):
            second = x               # a new runner-up (ignores repeats of first)
    return second

The idea. Keep the top two different values seen so far. A new champion pushes the old champion down to second place. A value equal to the champion changes nothing, which is how repeated maxima such as [5, 1, 5, 3] are handled.

Keep a second collection, seen = set(), next to result. Ask if x not in seen; when true, add x to both.

def dedupe(items):
    result = []
    seen = set()               # fast membership test: "have I met x before?"
    for x in items:
        if x not in seen:
            seen.add(x)
            result.append(x)   # first time we meet x: keep it
    return result

The idea. The list result remembers the order; the set seen answers “have I met this before?” instantly. Each tool does the job it is good at. Using two data structures together like this is very common.

By hand: put a finger at the start of each list. Which of the two numbers under your fingers goes into the output first?

While both fingers are still inside their lists (i < len(a) and j < len(b)): append the smaller of a[i] and b[j], and move that finger forward. When one list runs out, the rest of the other list is already sorted: add it all with merged.extend(a[i:]) and merged.extend(b[j:]).

def merge_sorted(a, b):
    merged = []
    i, j = 0, 0
    while i < len(a) and j < len(b):
        if a[i] <= b[j]:          # take the smaller front item (<= keeps a's item first on ties)
            merged.append(a[i])
            i += 1
        else:
            merged.append(b[j])
            j += 1
    merged.extend(a[i:])          # at most one of these two adds anything
    merged.extend(b[j:])
    return merged

The idea. The smallest item still waiting must be at the front of one of the two lists, because each list is sorted. So we only ever compare the two front items. This “merge” step is the heart of merge sort, which you will meet in Coding practice 3.

What should the numbers 0 + 1 + … + n add up to if none were missing? Compare that with what they actually add up to.

The full total is \(\frac{n(n+1)}{2}\) (in Python, n * (n + 1) // 2, where // divides and keeps a whole number). The missing number is that total minus sum(nums).

def missing_number(nums):
    n = len(nums)
    expected = n * (n + 1) // 2      # 0 + 1 + ... + n, if nothing were missing
    return expected - sum(nums)      # whatever is short is the missing number

The idea. If nothing were missing, the numbers 0 to n would add up to a known total. The list adds up to that total minus the missing number. So subtract.

Sum of the first n whole numbers
\[0+1+2+\dots+n=\frac{n(n+1)}{2}\]

Read: “zero plus one plus … plus n equals n times n-plus-one, over two”. Write the sum forwards and backwards and add the two rows: every column gives \(n\), there are \(n+1\) columns, so twice the sum is \(n(n+1)\). For \(n=3\): \(0+1+2+3=6=\frac{3\cdot4}{2}\).

Explain to an interviewer, in two or three sentences, why your merge of two sorted lists is \(O(n_a+n_b)\) and why that is better than gluing them and calling sorted().

Each comparison puts one item into the output and moves one of the two indices forward, and together the indices can only move \(n_a+n_b\) times, so the loop does at most \(n_a+n_b\) steps. Sorting the glued list costs \(O((n_a+n_b)\log(n_a+n_b))\) because it does not use the fact that each input is already sorted; the merge uses that fact to avoid the extra log factor.
The five steps for solving a coding problem
Read (input/output/edge cases) → examples by hand → brute force first → improve → test edge cases.
What does \(O(n)\) mean in plain words?
The number of steps grows in proportion to the input size: double \(n\), double the work.
Two rules to simplify a step count into Big-O
Keep only the fastest-growing term; drop constant multipliers. \(3n^2+5n+2=O(n^2)\).
Order these from fastest to slowest: \(O(n^2)\), \(O(1)\), \(O(n\log n)\), \(O(\log n)\), \(O(n)\)
\(O(1)\) < \(O(\log n)\) < \(O(n)\) < \(O(n\log n)\) < \(O(n^2)\)
Where does a \(\log n\) in a running time come from?
From halving (or splitting) the problem at every step: \(\log_2 n\) is the number of halvings from \(n\) down to 1.
Time of x in some_list vs x in some_set
List: \(O(n)\) (scans the items). Set: \(O(1)\) on average (hash look-up).
\(0+1+\dots+n=\;?\)
\(\dfrac{n(n+1)}{2}\). Used for the missing-number problem.
What does “in place, O(1) extra space” mean?
Change the input itself, using only a fixed number of extra variables, no new list as big as the input.
Two-pointer reversal: start positions and stop condition
left = 0, right = len(xs) - 1; swap and move inwards while left < right.
Merging two sorted lists: the key fact
The smallest remaining item is always at the front of one of the two lists, so compare only the two front items. Remember to add the leftovers.
Which edge cases should you always test?
Empty input, one element, all equal / duplicates, negatives (and zero), and a large input for speed.
