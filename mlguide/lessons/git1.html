Git keeps a save point of your project every time you ask it to, so you can always see what changed, go back, and try ideas without fear. GitHub keeps a copy online, which is also where employers will look at your work. In this lesson you put your course folder under Git, connect it to GitHub, and learn the handful of commands you'll use every day for the rest of your career.

What version control is, and why you want it

Have you ever had files called report_final.docx, report_final2.docx, report_final_REALLY.docx? That is version control done by hand, badly. Version control is software that does it properly: it remembers every saved version of every file in a project, who changed what and why, and lets you jump back to any of them.

Think of a video game with save points. Before the difficult level, you save. If it goes wrong, you reload. Git gives you unlimited save points for your code, each with a note saying what you did. In ML this matters even more than in ordinary programming:

  • Experiments. You'll change a model, the test error gets worse, and you'll want the exact code from yesterday's better run. With Git that's one command.
  • Fearless trying. On a branch you can try a wild idea without touching the working version.
  • Backup and sharing. Pushing to GitHub copies everything off your Mac.
  • Your portfolio. Recruiters for ML roles read GitHub profiles. A tidy repository per project, with a clear README and an honest history of commits, shows how you work better than any CV line.

Git versus GitHub. Git is a program on your Mac that keeps the history of a folder. It works entirely offline. GitHub is a website (owned by Microsoft) that stores copies of Git repositories online so you can back them up, share them and collaborate. Git is the camera; GitHub is the online photo album.

Why a separate staging area, instead of saving everything at once? Because it lets you choose. Say you fixed a bug in knn.py and also scribbled half-finished notes in notes.txt. You can add only knn.py and commit it as "Fix distance formula", a clean save point that contains exactly one idea.

Start by pressing git add ., then git commit, then git push: both files travel all the way to GitHub, and the dark box shows the real git status message at each moment. Then press Edit knn.py: it turns red ("modified") in the working folder. Press git commit straight away: nothing happens, because nothing is staged. Add it, commit, and notice the status line "Your branch is ahead of 'origin/main' by 1 commit" until you push. Finally make New notes.txt and see how Git treats an untracked file.

Step 1 · Check Git and introduce yourself

Git came with the Xcode Command Line Tools you installed in Set up your Mac. Open Terminal and check:

Type this

git --version

What you should see

git version 2.39.5 (Apple Git-154)

Any version from 2.28 onward is fine. If you get a pop-up asking to install developer tools, accept it and wait, then try again.

Every commit records who made it, so tell Git your name and email once. Use the same email you will use for GitHub, so your commits are linked to your profile. These settings are stored in a file in your home folder, ~/.gitconfig, and apply to every project.

Type these four lines (with your own name and email)

git config --global user.name "Asha Rao"
git config --global user.email "asha.rao@example.com"
git config --global init.defaultBranch main
git config --global core.editor "nano"
  • git config reads or changes Git's settings; --global means "for all my projects on this Mac".
  • user.name and user.email are written into every commit you make. The quotes keep a name with a space together.
  • init.defaultBranch main: name the main line of history main, as GitHub does (older Git used master).
  • core.editor "nano": if Git ever needs you to type a longer message, it opens nano, a simple text editor that shows its keys at the bottom (Ctrl + O then Return saves, Ctrl + X exits). Without this, Git opens vim, which baffles newcomers (to escape vim: press Esc, type :wq, press Return).

These commands print nothing when they work. Check with:

git config --global --list

What you should see

user.name=Asha Rao
user.email=asha.rao@example.com
init.defaultbranch=main
core.editor=nano

Step 2 · Turn your course folder into a repository

A repository (or "repo") is a folder whose history Git keeps. You make one with git init, inside the folder:

Type this

cd ~/ml-course
git init

What you should see

Initialized empty Git repository in /Users/you/ml-course/.git/

Git made a hidden folder, .git, where it will keep every save point. You never edit it by hand. (Delete .git and the history is gone, but your files stay.) The prompt doesn't change, but VS Code will now show Git information in its sidebar.

The most useful command in Git asks "what's going on?":

Type this

git status

What you should see (your list may differ)

Untracked means "files Git can see but isn't keeping history for yet". Look at that list: .venv/ is in it. That folder holds thousands of library files, rebuildable in two minutes with uv. It must never go into Git. The CSV data files don't belong either: they're not your work, they can be re-downloaded, and real datasets are often far too big for Git.

Step 3 · Keep junk out with .gitignore

A file called .gitignore lists names and patterns Git should pretend don't exist. In VS Code (with ~/ml-course open), choose File → New File…, name it .gitignore (with the leading dot), and type:

# the virtual environment: rebuild it with uv, never commit it
.venv/
# Python's and Jupyter's automatic files
__pycache__/
.ipynb_checkpoints/
# data files: re-downloadable, often large
*.csv
*.zip
# macOS folder settings
.DS_Store
  • Lines starting with # are comments.
  • A name ending in / means a folder and everything in it.
  • * means "any characters", so *.csv matches every file ending in .csv. (This pattern is called a glob; it's the same * that made zsh say "no matches found" in the setup lesson.)
  • .DS_Store is a hidden file Finder creates in every folder you open. Every Mac user's repos should ignore it.

Save it (⌘ + S) and run git status again:

What you should see now

On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	.gitignore
	notebooks/
	test.ipynb

nothing added to commit but untracked files present (use "git add" to track)

The environment and the data have vanished from the list. Only your own work is left, plus .gitignore itself, which should be committed so the rules travel with the project.

Never commit secrets. Passwords, API keys and tokens must never go into a repository, even a private one: once something is in a commit, it stays in the history even if you delete the file later, and bots scan GitHub for leaked keys within minutes. Keep secrets in a file listed in .gitignore (commonly .env).

Step 4 · Your first commit

Making a save point is two commands: choose what goes in (git add), then record it with a message (git commit).

Type this

git add .
git status
  • git add . stages everything in the current folder that has changed and isn't ignored (the dot means "this folder", as in the setup lesson). To stage one file, name it: git add test.ipynb.

What you should see

On branch main

No commits yet

Changes to be committed:
  (use "git rm --cached <file>..." to unstage)
	new file:   .gitignore
	new file:   notebooks/np1.ipynb
	new file:   notebooks/py1.ipynb
	…
	new file:   test.ipynb

"Changes to be committed" is the staging area. In Terminal these lines are green; untracked and modified files are red.

Type this

git commit -m "Set up course folder with notebooks"
  • -m means "the message follows", in quotes. Without -m, Git opens nano for you to write one.

What you should see

[main (root-commit) 3f2a1c4] Set up course folder with notebooks
 24 files changed, 6081 insertions(+)
 create mode 100644 .gitignore
 create mode 100644 notebooks/py1.ipynb
 …

main is the branch; root-commit means "the very first one"; 3f2a1c4 is the commit's short ID (yours will be different). "Insertions" counts lines added. Run git status again: nothing to commit, working tree clean. Everything is saved.

A commit ID is a checksum. The full ID is a 40-hex-digit SHA-1 hash of the commit's contents, its message, its author and its parent commit. Like a CRC on a data frame, flip one bit anywhere and the hash changes completely, so Git can detect corruption, and because each commit includes its parent's hash, the history forms a tamper-evident chain. The 7-character short form is enough to name a commit in practice.

Good commit messages

Write the message as a short instruction that completes the sentence "This commit will …": Add KNN classifier, Fix off-by-one error in slicing, Plot test error against k. Keep it under about 60 characters. Avoid update, stuff, asdf: in three weeks you'll be scanning the history for "where did the test error drop?", and only good messages will tell you. Commit small and often: one idea per commit.

Step 5 · The daily loop, history and differences

Now make a real change. In VS Code create README.md in ~/ml-course containing these three lines (# at the start of a line makes a heading in Markdown, the formatting language GitHub uses for READMEs):

# ML course

My work for ML Foundations, months 1–3.

Then commit it. This is the loop you will repeat every day:

The daily loop

git status
git add README.md
git commit -m "Add README"

Now change the README: replace the last line with two new lines, and save.

# ML course

My work for ML Foundations, months 1–3, on a MacBook Air.
Started: October 2026.

Before adding, ask Git exactly what changed:

Type this

git diff

What you should see

diff --git a/README.md b/README.md
index 5d1c2e3..8a9b0f1 100644
--- a/README.md
+++ b/README.md
@@ -1,3 +1,4 @@
 # ML course

-My work for ML Foundations, months 1–3.
+My work for ML Foundations, months 1–3, on a MacBook Air.
+Started: October 2026.

Read it line by line. --- is the old version, +++ the new. @@ -1,3 +1,4 @@ says "the old file's lines 1 to 3 became the new file's lines 1 to 4". Then a line starting with a space is unchanged, - was removed (red in Terminal), + was added (green). Changing a line shows up as one removal plus one addition. If the diff is long, Git shows it a page at a time: press Space for more and q to quit.

git diff shows changes you haven't staged yet. After git add, use git diff --staged to see what you're about to commit. Commit this change with git commit -am "Describe my setup in README": the extra -a means "add every already-tracked file that changed, then commit", a shortcut that never picks up brand-new files.

See the history

git log --oneline

What you should see

a91e07d (HEAD -> main) Describe my setup in README
6b2d4f8 Add README
3f2a1c4 Set up course folder with notebooks

Newest first, one line per commit: short ID and message. HEAD -> main marks where you are now. Plain git log shows more detail (author, date, full ID); press q to leave it.

Step 6 · Put it on GitHub

Create your account

  1. Go to github.com and click Sign up. Use the email you gave to git config.
  2. Choose your username carefully: it will appear in every link you put on your CV (github.com/asharao). Your real name, or close to it, is best. Avoid nicknames you'd be embarrassed by in an interview.
  3. Verify your email, and set up two-factor authentication (GitHub requires it for anyone who pushes code). An authenticator app on your phone is the simplest option.
  4. Add a profile photo and one line about yourself ("ECE undergraduate learning ML and computer vision"). You'll polish the profile as projects arrive.

Create an empty repository

Top right, click + → New repository. Name it ml-course. Choose Private for this one (it's your study folder; your portfolio projects will be public). Don't tick "Add a README", ".gitignore" or "license": your local repository already has history, and GitHub's starter files would conflict with it. Click Create repository. GitHub shows a page with commands; you'll use the ones below.

Connect your Mac to GitHub: two ways

GitHub must be sure that pushes really come from you. Your GitHub password doesn't work in Terminal (that was switched off in 2021). Choose one of these:

Way A (recommended): the GitHub CLI, gh. A small official program that logs you in through the browser and sets everything up. Download the macOS installer from cli.github.com and run it (or, if you have Homebrew, brew install gh). Then:

Type this, and answer the questions

gh auth login

What you should see (choose with the arrow keys and Return)

? Where do you use GitHub? GitHub.com
? What is your preferred protocol for Git operations on this host? HTTPS
? Authenticate Git with your GitHub credentials? Yes
? How would you like to authenticate GitHub CLI? Login with a web browser

! First copy your one-time code: 1A2B-3C4D
Press Enter to open github.com in your browser...
✓ Authentication complete.
- gh config set -h github.com git_protocol https
✓ Configured git protocol
✓ Logged in as asharao

The browser asks you to paste the 8-character code and approve. After this, git push just works. Bonus: gh repo create can make GitHub repositories without visiting the website.

Way B: HTTPS with a personal access token. A personal access token (PAT) is a long password-like string that you generate on GitHub and use instead of your password. On GitHub: your photo (top right) → Settings → Developer settings (bottom of the left menu) → Personal access tokens → Fine-grained tokens → Generate new token. Give it a name ("MacBook"), an expiry (90 days), choose Only select repositories → ml-course (later, "All repositories"), and under Repository permissions set Contents to Read and write. Generate it and copy it immediately: GitHub shows it only once. The first time git push asks for a password, paste the token. macOS stores it in your Keychain, so you won't be asked again until it expires.

Link and push

Type this (with your username)

git remote add origin https://github.com/asharao/ml-course.git
git push -u origin main
  • git remote add origin URL: remember this GitHub address under the short name origin (the standard name for "the main online copy"). Copy the URL from your repository's page.
  • git push origin main: send the commits of branch main to origin.
  • -u ("upstream"): also remember that local main goes with origin/main, so next time plain git push is enough.

"rejected … fetch first" when pushing means GitHub has commits you don't have (for instance, you edited the README on the website, or ticked "Add a README" when creating the repo). Run git pull to bring them down and combine them with yours, then push again.

Step 7 · Clone and pull

git clone URL copies a whole repository, with all its history, into a new folder. It's how you'll get the code that accompanies papers and courses, and how you'd set up your own project on a second computer.

Try it (this makes a new folder, ~/ISLP_labs)

cd ~
git clone https://github.com/intro-stat-learning/ISLP_labs.git
cd ISLP_labs
git log --oneline | head -5

What you should see

Cloning into 'ISLP_labs'...

…followed by the five most recent commits of the official ISLP labs repository: the book's Python labs as notebooks. (| head -5 pipes the log into head, which keeps only the first 5 lines.) If anyone updates a repository you cloned, git pull inside it fetches and merges their new commits.

Step 8 · Branches: try an idea safely

A branch is a separate line of commits. main is the one you've been using. Make a new branch when you want to try something that might not work: if it fails, you delete the branch and main never knew; if it works, you merge it into main.

Type this (in ~/ml-course)

git switch -c try-notes
#   ...edit README.md in VS Code: add a line "Goal: build a KNN classifier from scratch."
git commit -am "Add learning goal to README"
git switch main
#   ...look at README.md in VS Code: the new line is gone (it lives on try-notes)
git merge try-notes
git branch -d try-notes
  • git switch -c try-notes: create a branch called try-notes and switch to it. (Older guides write git checkout -b try-notes; it does the same.)
  • git switch main: go back to main. Git rewrites the files in your folder to match that branch, which is why the line seems to vanish. It isn't lost.
  • git merge try-notes: bring the branch's commits into main.
  • git branch -d try-notes: delete the branch label, now that its work is in main. git branch on its own lists branches, with a * on the current one.

What you should see after the merge

Updating a91e07d..c4e8b20
Fast-forward
 README.md | 1 +
 1 file changed, 1 insertion(+)

Fast-forward means main hadn't moved since you branched, so Git just slid main forward to the branch's newest commit. If both had new commits touching the same lines, Git would stop and ask you to resolve a merge conflict; you'll meet those when you work with others, and VS Code shows them with buttons to pick a side.

Commit or stash your work before switching branches: Git refuses to switch if it would overwrite unsaved changes, and tells you so.

How this becomes your portfolio

From the first project of this course onward, give every project its own public repository (for example knn-from-scratch, islp-linear-regression, mnist-mlp-pytorch). Your ml-course folder stays your private notebook. A good project repository has:

  • a README that a recruiter can read in one minute (template below);
  • clean code in .py files plus a notebook that shows results, with every cell run top to bottom;
  • a requirements.txt listing the libraries, so anyone can rebuild your environment. Make it with uv pip freeze > requirements.txt (the > sends the output into a file instead of the screen);
  • a .gitignore (no .venv, no large data, no secrets) and instructions to download the data instead;
  • a history of small, well-named commits: it shows how you think.

A README template (Markdown) you can copy into each project:

# KNN classifier from scratch

Classifies 2-D points with k-nearest neighbours, written in plain Python
and checked against scikit-learn's KNeighborsClassifier.

## Results
![Decision boundary for k = 1 and k = 15](figures/boundary.png)

## How to run
    uv venv --python 3.12 && source .venv/bin/activate
    uv pip install -r requirements.txt
    python knn.py

## What I learned
- Small k gives a jagged boundary (low bias, high variance) ...

On your GitHub profile, pin your best six repositories (Profile → Customize your pins). That is the first thing a reviewer sees.

In interviews you will be asked about your GitHub projects: "walk me through this repo", "why did you choose k = 7?", "how would you make it faster?". Every project should be one you can explain line by line. Git questions themselves are usually practical: the difference between git add and git commit; what git pull does (fetch, then merge); how you'd undo a change; what a merge conflict is.

Notebooks in Git

A .ipynb file stores outputs (including images) as well as code, so diffs are long and noisy. Two habits help: before committing, restart the kernel and run all cells so the saved outputs are clean and in order; and keep reusable code in .py files, which diff nicely. VS Code's Source Control panel (the branching icon in the left bar) also shows notebook diffs cell by cell, and can stage and commit with buttons if you prefer that to Terminal.

Check yourself

You edited knn.py and saved it in VS Code. Which command puts that change into the next commit?

  1. git commit
  2. git add knn.py
  3. git push
  4. git status
Saving a file changes only the working folder. git add moves the change to the staging area; then git commit records it, and git push sends commits to GitHub. git status only reports.

Which line in .gitignore stops all CSV files being committed?

  1. csv
  2. .csv/
  3. ignore *.csv
  4. *.csv
* matches any characters, so *.csv matches every name ending in .csv. .csv/ would mean a folder called ".csv"; csv only a file or folder named exactly "csv".

What is the difference between Git and GitHub?

  1. Git keeps history on your computer; GitHub is a website that stores copies of Git repositories online
  2. They are two names for the same program
  3. GitHub is the newer version of Git
  4. Git is for code, GitHub is for data
Git works entirely offline on your Mac. GitHub hosts repositories online for backup, sharing and collaboration (GitLab and Bitbucket are alternatives).

git status says "Your branch is ahead of 'origin/main' by 2 commits". What should you do to update GitHub?

  1. git pull
  2. git add .
  3. git push
  4. git commit
"Ahead" means you have 2 commits that GitHub doesn't. Pushing sends them. Pulling goes the other way.

In a git diff, a line starting with - means…

  1. a line that was added
  2. a line that was removed (or the old version of a changed line)
  3. a comment
  4. an error
- lines are from the old version, + lines from the new; a changed line appears as one of each. Lines starting with a space are unchanged context.

Why should .venv/ be in .gitignore?

  1. Git can't read it
  2. It contains your passwords
  3. GitHub forbids Python files
  4. It's thousands of rebuildable library files, specific to your Mac; the project should list its libraries (requirements.txt) instead
The environment can be recreated in minutes with uv from a list of requirements, and its files are big, numerous and machine-specific. Committing it bloats the repository and breaks on other computers.

A diff header reads @@ -1,3 +1,4 @@. How many lines did that part of the old file have?

-1,3: the old version, starting at line 1, 3 lines long. +1,4: the new version, starting at line 1, 4 lines long.
